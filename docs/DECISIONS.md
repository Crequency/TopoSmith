## D-01 内核是"推演器"，不是"仿真器"

- **背景**：用户需求含"模拟两点通讯速度、模拟数据包链路、模拟可达性"。
  直觉做法是做逐包离散事件仿真（Packet Tracer / ns-3 路线）。
- **决策**：内核是**确定性推演内核**（deduction kernel），不做逐包事件仿真。
- **理由**：算力差 2–3 个数量级（1 Gbps ≈ 1.5 Mpps；单线程引擎 10⁶–10⁷ 事件/秒），
  而用户要的六个能力全部是**图算法 + 约束求解**，不需要时间推进。
  推演换来毫秒级响应、纯前端、可静态托管、结果确定可回归。
- **代价**：不能逐包回放、不能跑真实协议报文、不提供设备 CLI。
  这些已写入 `NG-01`–`NG-05` 与 `00-overview.md` §5。
- **状态**：✅ 生效（2026-09-17）

## D-02 零后端

- **背景**：多人协作、云场景库等需求天然想要后端。
- **决策**：M0–M2 构建产物为纯静态文件；不引入任何服务端依赖。
- **理由**：可离线、可内网、可嵌入、无服务器成本与可用性风险。
  M3 若做协作，后端只做 CRDT 中继，**推演逻辑仍在前端**。
- **代价**：无云端同步、无场景库共享（M3 之前）。
- **状态**：✅ 生效

## D-03 项目名：TopoSmith（拓扑匠）

- **背景**：候选 Netloom（网织）、TopoLens（网镜）、NetForge（拓坊）、TopoSmith（拓扑匠）。
- **决策**：**TopoSmith / 拓扑匠**（用户选定 D）。
- **理由**：`smith`（匠人）对应"手工精细标注端口、速率、线缆"的产品气质，
  与"自动发现/自动拓扑"类工具形成区分；`Topo` 直接表达拓扑。
- **代价**：名字较长；域名/npm 占用情况**未核实**（本机出网受限），
  若不可用需追加一条改名决策。
- **状态**：✅ 生效（2026-09-17）

## D-04 M0 渲染用 Canvas 2D，WebGL 留到 M2

- **背景**：此前规划"画布必须 WebGL"，理由是 DOM/SVG 在 1–2k 元素掉帧。
- **决策**：M0 用 **Canvas 2D**，渲染器抽象为 `draw.ts`（纯绘制）+ `Canvas.tsx`（交互），
  达到性能门槛后再切 PixiJS/WebGL。
- **理由**：M0 的目标是打通推演链路而非渲染压测；Canvas 2D 在 300–500 节点足够舒适，
  且能保证 M0 按期交付。抽象层保证换渲染器不牵动交互与状态。
- **代价**：千级节点在 M0 会卡。**硬门槛**：若 300 节点/500 链路 < 50fps，
  M2 必须切 WebGL（NFR-01），不允许用"少放设备"绕过。
- **状态**：✅ 生效；M2 复审

## D-05 l2 / l3 / dns / diag 合并进 engine 包

- **背景**：原规划把它们拆成独立 workspace 包。
- **决策**：合并为 `packages/engine/src/{l2,l3,diag}` 子目录，`catalog` 与 `schema` 保持独立。
- **理由**：它们共享同一个 `World` 类型且互相调用，拆包只会制造循环依赖或额外类型包；
  且没有独立消费者。`catalog`（纯数据，可被文档/清单复用）与 `schema`（输入契约边界）
  有真实独立价值。
- **代价**：engine 包会变大。等出现第二个消费者（如"只做 DNS 教学"的应用）再拆，成本更低。
- **状态**：✅ 生效

## D-06 DHCP 按客户端 ID 字典序确定性分配

- **背景**：真实 DHCP 是先到先得，需要"时间"与"请求顺序"概念。
- **决策**：按**客户端 ID 字典序**决定池内偏移量，完全不依赖时间。
- **理由**：保证同输入同输出（NFR-03）。地址稳定 → 导入导出、回归测试、
  截图对比、教学答案全部可复现。
- **代价**：与真实"先到先得"不同（用户看不到"某台设备抢到了 .100"这类现象）。
  该差异在设备检查器里以文案说明。
- **状态**：✅ 生效

## D-07 引擎的确定性纪律：不用随机、不用时钟、不遍历插入序做决策、不改输入

- **背景**：证据链要做回归测试，就必须逐字节稳定。
- **决策**：引擎内禁止 `Math.random` / `Date.now`；凡"选一个"都按显式排序键；
  `buildWorld` 不 mutate 输入，诊断不 mutate `World`。
- **理由**：结果是可断言的（测试断言 `steps[].code` 序列），
  也让"同一拓扑在两个浏览器里给出不同答案"这类诡异 bug 在结构上不可能。
- **代价**：需要显式传时间与排序键，代码略啰嗦。
- **状态**：✅ 生效

## D-08 线缆物理约束必须真实，"降速"与"不通"分开

- **背景**：多数模拟器把线缆当无约束的"连线"，速率由端口决定。
- **决策**：实现五条硬约束（`03-catalog.md` §3）：电口≠光口直连、铜缆 > 100 m 不通、
  CAT6 的 10G 仅 55 m、CAT6e 是俗称（标准名 CAT6a）、光纤速率由模块决定。
  并严格区分 **down（不通）** 与 **降速（up 但速率受限）**。
- **理由**：这是产品差异化所在——用户把端口速率和线缆类型认真标注，
  就是因为他们在真实工程里被这些约束坑过。
- **代价**：目录数据必须持续维护且带出处，否则可信度崩塌（见风险登记）。
- **状态**：✅ 生效

## D-09 UI 样式一律用 Tailwind 类名内联

- **背景**：用户明确要求"编写风格为 in class tailwind"。
- **决策**：所有样式写在 `className` 上；不新增语义化 CSS 类；不用 `@apply` 抽公共样式，
  需要复用就抽 React 组件。仅 `index.css` 内 `@import "tailwindcss"` 与极少数全局基线例外。
- **理由**：用户指定；同时避免"样式改一处、影响一片"的隐式耦合。
- **代价**：`className` 会较长；重复视觉需要靠组件化而非 CSS 复用解决。
- **状态**：✅ 生效（2026-09-17）

## D-10 开发服务器：0.0.0.0:31006，经 DevHub 启停

- **背景**：用户指定端口与信任域名；全局规则要求长驻服务统一由 `devctl` 管理。
- **决策**：`vite.config.ts` 硬编码 `port: 31006` + `strictPort: true` + `host: '0.0.0.0'`，
  `allowedHosts` 含 `toposmith.dev-u26-001.services.local`；
  启停一律走 `devctl start/stop toposmith dev`，**禁止裸 `pnpm dev &`**。
- **理由**：端口即所有权（DevHub R5）；DevHub 只登记不分配端口，端口由项目自身决定。
- **代价**：端口冲突时需人工决定谁让位，不自动漂移。
- **状态**：✅ 生效

## D-11 一个端口最多一根线缆（M0）

- **背景**：真实设备支持链路聚合、堆叠、多宿主。
- **决策**：M0 强制"一端口一线缆"，违反时拒绝创建并说明。
  **例外：无线端口（radio）可承载多条关联** —— 一个 AP 的 radio 天然同时服务多台客户端，
  这不是聚合，而是共享介质。因此"一端口一线缆"只约束有线端口。
- **理由**：聚合需要引入"聚合组"实体与基于哈希的选路，成本远超 M0 收益；
  强行允许多线缆会让"这条链路速率是多少"变成不可判定问题。而无线若不允许多关联，
  连"手机和笔记本同时连一个 AP"都画不出来，产品直接不可用。
- **代价**：无法建模双上行冗余与 LACP；`linksByPort` 必须是数组而非单值（已在引擎中如此实现）。
  M3 引入聚合组实体后再放开有线侧。
- **状态**：✅ 生效（2026-09-17 补充无线例外）；M3 复审有线侧

## D-12 无线关联建模为一根 `wireless` 线缆

- **背景**：无线是共享介质，与"点到点线缆"的物理模型不同。
- **决策**：把"STA 关联 AP"表达为 `type: 'wireless'` 的 Cable，
  使无线客户端能复用同一套广播域 BFS / ARP / 路径推演代码；共享介质折扣放在
  带宽计算阶段（§5 of `05-engine.md`），不改链路协商速率。
- **理由**：用一条代码路径处理有线与无线，避免两套并行的二层逻辑互相漂移。
- **代价**：无线链路在 UI 上看起来像一根线（用虚线区分），
  不表达"同一 AP 下所有客户端共享空中接口"的空间关系——靠结论文案补齐。
- **状态**：✅ 生效

## D-13 DNS 缓存放在会话，不进 Schema

- **背景**：缓存命中/过期是 DNS 演示的关键，但缓存不是拓扑事实。
- **决策**：`resolve()` 接收可选的 `DnsSessionCache` 参数；缓存由 UI store 持有，可清空。
- **理由**：保持引擎纯函数（NFR-03），同时保留"第二次查询命中缓存"的教学效果。
- **代价**：调用方需负责传递缓存；刷新页面后缓存清空（可接受，甚至更符合直觉）。
- **状态**：✅ 生效

## D-14 M0 不实现 ACL 与 STP

- **背景**：两者都影响可达性与路径，属"应该有"的能力。
- **决策**：M0 不实现；在 `07-diagnostics.md` §6 明确披露为已知简化，M2 补。
- **理由**：ACL 需要规则模型 + 匹配顺序 + 方向语义，STP 需要拓扑收敛与端口状态机，
  两者都会显著拉长 M0。先把"物理约束 + VLAN + 路由 + NAT + DNS"这条主线做扎实。
- **代价**：含环路或含策略的网络，M0 结论可能与真机不同——**必须披露**，不做静默近似。
- **状态**：✅ 生效；M2 复审

## D-15 本机环境：代理、只读全局 store、pnpm 11 不读 .npmrc

- **背景**（三者在落地时全部实测踩到，非推测）：
  1. **代理**：会话环境变量 `http_proxy/https_proxy = http://192.168.1.161:40404`，该地址
     `No route to host`。而 `/etc/profile.d/proxy.sh`（系统登录 shell 的配置）写的是
     **`10.0.30.81:40404`，实测可用**（经它访问 registry 返回 200）。
     两者不一致的原因是 **2026-09-14 做过一次代理迁移**——`/etc` 下留有一批
     `*.bak-pre-proxy-20260914` 备份文件，而本会话的进程环境仍是迁移前的旧值。
     结论：**会话继承的代理是过期值，不是"代理不可用"**。直连 registry 同样可用。
  2. **store**：pnpm 默认 store 在 `~/.local/share/pnpm/store`，位于会话工作区之外，
     被 DSH 文件沙箱置为只读，导致 sqlite 索引报 `[ERR_SQLITE_ERROR] unable to open database file`。
  3. **配置位置**：pnpm 11 **不再读取项目 `.npmrc`**（`pnpm config get store-dir` 返回 `undefined`），
     配置必须写进 `pnpm-workspace.yaml`。
- **决策**：
  - 安装/构建命令显式绕过会话里的过期代理
    （`env -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY pnpm …`）；
    若将来需要走代理，正确地址是 **`http://10.0.30.81:40404`**（来自 `/etc/profile.d/proxy.sh`）。
  - `pnpm-workspace.yaml` 设 `storeDir` 指向工作区内的 `.pnpm-shared-store`，并
    `allowBuilds: esbuild: true`；
  - 保留 `.npmrc` 但注明"对 pnpm 11 不生效，仅为 npm 与文档留底"。
- **理由**：环境变量优先级高于配置文件，过期代理只能从命令层绕过；
  store 位置与 pnpm 配置位置必须在 pnpm 真正读取的地方声明。
- **代价**：`storeDir` 是绝对路径，换机器/换工作区必须同步修改（文件内已标注警告）；
  `pnpm dev` 会做依赖状态检查，store 配置丢失时连启动开发服务器都会失败。
- **状态**：✅ 生效（2026-09-17，环境限制，非项目问题）

## D-16 在用户给定设备清单之外，增加 AP / OLT / 云出口三类设备

- **背景**：用户清单为：光猫、路由器、交换机、计算机、可移动设备、嵌入式设备。
- **决策**：追加 `ap`（无线 AP）、`olt`（局端 OLT）、`cloud`（云/互联网出口）。
- **理由**：
  - 用户要求 `1Gbps/2.5Gbps/10Gbps Wifi` 这类接口与 Wireless 接线类型，
    没有 AP 就无处挂载；
  - 用户要求 PON 与 10G-EPON，而 PON 是点到多点接入网，
    没有 OLT 则光猫的 PON 口悬空；
  - 没有公网侧目标，"NAT 转换点"与"DNS 转发链"两个核心演示无法进行。
- **代价**：设备清单超出用户原始枚举（需在 UI 分组中明确区分"内置扩展"）。
- **状态**：✅ 生效（2026-09-17）

## D-17 家用网关（光猫/路由器）的 LAN 口与 WLAN 内部桥接；桥接模式 = 透明网桥

- **背景**：光猫与路由器既是三层设备（终结广播域），又把 LAN 交换口与 WiFi 桥接在同一个二层域里。
  若严格按"三层设备终结广播域"处理，光猫自己的 WiFi 客户端将无法从光猫的 DHCP 拿到地址 ——
  模型一上线就与真实家庭网络不符。
- **决策**：
  1. **路由模式**的光猫/路由器：其 `role === 'lan'` 的端口（含 WLAN）在设备**内部桥接**成 VLAN 1 的
     广播域，三层接口浮在这个桥上（`bridgesLanPorts`）。
  2. **桥接模式**的光猫/路由器：整机视为**透明网桥**，在所有端口间二层转发（`isL2Forwarder`）。
- **理由**：这是"光猫改桥接 + 路由器拨号"与"家用网关 LAN/WiFi 同域"两种最常见拓扑能被正确推演的前提。
- **代价**：设备行为不再能只由 `kind` 决定，还要看 `accessMode`；桥接模式下"谁做 NAT/DHCP"变成
  用户必须自己配对的责任（推演会给出 `NAT_MISSING` 提示）。
- **状态**：✅ 生效（2026-09-17）

## D-18 无线关联校验 SSID，并新增 `SSID_MISMATCH` 原因码

- **背景**：无线连接失败在现实中最高频的原因就是 SSID 不一致（或大小写不符）。
- **决策**：建立无线关联时，若两端都配置了 SSID 且不相同 → 链路直接 down，
  原因码 `SSID_MISMATCH`，文案提示大小写敏感。
- **理由**：这是一个成本极低、教学价值极高的校验；不校验的话，工具会给出"无线通"的假结论。
- **代价**：用户必须为 STA 与 AP 填写一致的 SSID（目录模板已给出默认值 TopoSmith-Home）。
- **状态**：✅ 生效（2026-09-17）

## D-19 DevHub 登记与实例状态需要放开文件沙箱

- **背景**：DevHub 的登记表 `~/.devhub/registry/projects.json` 与实例状态目录
  `~/.devhub/state/<session>/` 都在会话工作区之外，而本机文件沙箱为 `workspace-write`，
  写入会被拒（实测报 `Read-only file system`）。但全局规则 R9/R11 要求：
  长驻开发服务器必须先 `devctl probe` → `register` 才能 `start`，**禁止裸 `pnpm dev &`**。
- **决策**：登记与启动动作以 `danger-full-access` 提权重试一次（仅此两类命令需要），
  并把「探测 → 提报登记条目 → 登记 → 启动 → 验证」合并为一次操作，减少重复打扰。
- **理由**：规则与沙箱的冲突只能由用户在提权提示上裁决；把步骤合并后，用户一次授权即可完成
  M0 的启动验证，而不是被连问四次（register / state 写入 / meta 写入 / 日志写入）。
- **代价**：后续每次启停开发服务器都可能需要一次提权确认；这是环境与规则的固有摩擦，
  不由项目代码解决。
- **状态**：✅ 生效（2026-09-17）

## D-20 图标库选型：Lucide（ISC）

- **背景**：需要"成熟的、商用免费的"图标，且要同时用于**画布（WebGL/Canvas）**与 DOM 面板。
  候选：iconfont.cn 图标字体、Font Awesome Free、Material Symbols、Lucide。
- **决策**：选 **Lucide 1.46.0**（ISC 许可，3676 个图标，按需引入）。
- **理由**：
  1. **许可**：ISC 与 MIT 同等宽松，商用与闭源分发均可，无需在 UI 上署名（NFR-11）；
     iconfont.cn 是平台而非许可，单图标授权状态需逐个确认，不适合作为项目基础设施。
  2. **画布友好**：Lucide 的图标数据是 `[标签名, 属性][]` 的**几何路径**，
     可直接构建 `Path2D` 描边；而图标字体方案必须额外加载字体文件、用私有区码位
     `fillText` 绘制，字体加载失败时会静默显示成方框。
  3. **一份数据两处用**：`lib/icons.ts` 同时导出 `strokeIcon`（Canvas）与 `Icon`（SVG 组件），
     画布与面板不可能出现"两套图标不同形"的漂移。
  4. **可摇树**：只引入用到的 30 个图标，构建体积增加约 25 KB（gzip 后约 9 KB）。
- **代价**：图标是 SVG 路径而非字体，无法用 CSS `content` 直接插入；
  需要在 `strokeIcon` 里做一次坐标系缩放（24×24 → 目标尺寸）与线宽反补。
- **状态**：✅ 生效（2026-09-17）

## D-21 画布交互约定：左键=选择/移动/框选，平移交给中键·右键·空格

- **背景**：引入框选后，"拖动空白"同时被"平移画布"和"框选"需要。
- **决策**：
  - 左键拖空白 = **框选**（相交即选中）；左键拖设备 = 移动（多选时整组移动）；
  - **平移** = 中键拖动 / 右键拖动 / 空格+左键拖动；
  - `Shift`+左键 = 切换选中；`Ctrl/Cmd+A` = 全选；`Esc` = 取消连线并清空选择；
  - `Delete`/`Backspace` = 删除选中（输入框聚焦时不触发）；
  - 吸附：网格 8 单位 + 节点参考线，阈值 7 **屏幕像素**（按当前缩放换算成世界单位，
    缩放后手感一致）；按住 `Alt` 临时关闭吸附。
- **理由**：框选是拓扑编辑的高频动作，值得占用左键拖拽；平移有中键/空格三种等价入口，
  在触控板与鼠标上都够用。阈值按屏幕像素而非世界单位，是为了让手感不随缩放漂移。
- **代价**：只熟悉"左键拖动平移"的用户需要重新适应（画布右下角常驻操作提示）。
- **状态**：✅ 生效（2026-09-17）

## D-22 流向动画：虚拟粒子 + 速率对数映射 + 失败停在阻断点

- **背景**：需要"用动画表示数据途径的链路流向与速度"。
- **决策**：纯 UI 层的动画模型（`lib/flow.ts`），不参与推演：
  - 沿路径铺粒子，**推进速度 = 该段链路速率的对数映射**
    （`55 × (1 + log10(速率/100))`，即 100M≈55、1G≈110、10G≈165 世界单位/秒）；
  - 沿线绘制方向箭头表示流向；
  - 数据包链路模式逐跳停顿时 340 ms，并高亮当前跳；
  - **诊断失败时把 `stopAt` 设为路径终点**，粒子停住并显示红色脉冲与"数据到此中断"；
  - 支持暂停/重放/0.5×–4× 倍速；`prefers-reduced-motion` 时不自动播放；
  - 动画状态放在 `useRef` 里由 rAF 直接驱动重绘，**不触发 React 逐帧渲染**。
- **理由**：速度必须来自真实链路速率，否则"看快慢"这件事就是假的；
  逐跳停顿与阻断点脉冲把"哪里慢/哪里断"变成一眼可见的结论。
- **代价**：动画需要每帧重绘整张画布（Canvas 2D 在千级节点下需要 M2 的 WebGL 方案兜底）。
- **状态**：✅ 生效（2026-09-17）

## D-23 hop 必须携带"二层实际经过的链路"（transitLinkIds）

- **背景**：这是本轮**由动画暴露出来的一处真实引擎缺陷**。hop 记录的是**三层转发决策**，
  而交换机/AP 不做三层决策，因此"笔记本 → 光猫"这一跳中间其实还穿过了
  `笔记本↔AP`（无线 1201 Mbps）、`AP↔交换机`、`交换机↔光猫`（1 Gbps 网线）三段链路，
  但它们在 hop 里完全不存在。
  后果有两个：① 带宽诊断把瓶颈报成 **1.2 Gbps**（无线段），而真实瓶颈是那条千兆网线；
  ② 流向动画在两个三层设备之间画一条**穿过交换机的直线**，看起来像"飞过去"。
- **决策**：`traceDomainPath` 在做广播域 BFS 的同时记录走过的链路序列，
  写入 `Hop.transitLinkIds`；带宽统计与流向动画**一律以这条序列为准**
  （拿不到时才回退到 hop 自身的出接口链路）。
- **理由**：路径必须等于"数据实际走过的每一根线"。少了二层链路，
  整个产品最核心的两个输出（能跑多快、怎么走的）都是错的。
- **代价**：`metrics.hops` 的条目数会多于三层跳数（这是正确的，链路段数 ≠ 跳数）；
  BFS 只能取一条最短路，等价多路径（双上行）场景仍只显示其中一条（已列入已知简化）。
- **状态**：✅ 生效（2026-09-17）；回归测试：
  `瓶颈必须计入二层穿过的链路：无线 1201 Mbps 不得掩盖 1G 网线（D-23）`

## D-24 撤销/重做：快照栈 + 合并窗口 + 拖动事务

- **背景**：多选与批量删除上线后，"误删 10 台设备无法恢复"成了最痛的问题。
- **决策**：实现基于**场景快照**的历史栈（`lib/history.ts`，上限 60 条），三个关键机制：
  1. **快照**：直接存整份 `Scenario`（10 设备仅几 KB），不做反向补丁 ——
     反向补丁要覆盖每一种编辑动作，正确性风险远大于那点内存；
  2. **合并窗口**：相同 `mergeKey` 且间隔 < 1.2 秒的连续改动只记一条 ——
     否则在名称输入框里敲 5 个字会产生 5 条历史，"撤销"退化成退字符；
  3. **拖动事务**：画布在 pointerdown 时 `beginHistory`、pointerup 时 `commitHistory`，
     整段拖动（几十帧）只算一条；若结束时状态引用未变则丢弃该事务。
- **理由**：历史栈的正确性比精细度重要 —— 用户能预期"撤销回到上一个有意义的状态"，
  而不是"退回 60 分之 1 帧"。
- **代价**：拖动过程中不能撤销中间帧（这是刻意的）；快照式历史在超大拓扑下内存占用较高
  （千级节点需要改为按需快照或补丁，已列入 M2 待办）。
- **状态**：✅ 生效（2026-09-17）

## D-25 端口图元化：端口常驻卡片、可点击编辑、作为连线的真正端点

- **背景**：原先端口是"选中设备后才出现的方块"，连线是"设备中心到设备中心"，
  端口在拓扑图上没有存在感，用户看不出哪根线插在哪个口上。
- **决策**：
  1. 设备卡片底部常驻**端口条带**，端口按介质画成对应形状（端口图元布局在 `lib/ports.ts`，
     尺寸分档 + 自动换行，5 口到 26 口共用一套代码）；
  2. 端口图元**优先于卡片本体**被命中：点击端口 = 选中该端口并打开端口详情，
     按住卡片空白处才是拖动设备；
  3. 连线**从端口图元接入点出发**，以三次贝塞尔"下垂电缆"曲线接到对端端口；
  4. 端口图元与卡片底边之间画一条**引出线**，让"电缆插在这个口上"可见 ——
     电缆本体画在卡片下层（避免遮挡卡片内容），引出线画在卡片上层（衔接两者）。
- **理由**：端口是本产品最核心的建模对象（速率、介质、VLAN 都挂在端口上），
  它必须在图上"看得见、点得到、连得上"，否则用户只能靠猜。
- **代价**：卡片布局复杂度上升（端口条带占 30 单位高度，地址行被压缩）；
  26 口设备图元只有 7×8 单位，端口名放不下时只在悬停提示与详情面板里显示。
- **状态**：✅ 生效（2026-09-17）

## D-26 速率配色：1G 红 / 10G 绿、对数刻度、范围外靠亮度区分

- **背景**：用户要求"为不同速度的连线标注不同的颜色，10Gbps 绿、1Gbps 红，
  具体颜色均匀分配到所有连线速度范围中"。
- **决策**（`lib/speed-color.ts`）：
  - 色相锚点：**1 Gbps → 0（红）**、**10 Gbps → 145（绿）**；
  - 两个锚点之间按**对数刻度**（每 10 倍速率跨越整段色相）均匀分配：
    2.5G ≈ 58（琥珀）、5G ≈ 101（黄绿）；
  - 超出 1G–10G 时色相钳制，改用**亮度**继续区分：100M 比 1G 更暗、100G 比 10G 更亮 ——
    否则所有低速链路会挤在同一个红色上，看不出差别；
  - 应用位置：**标签文字色 + 标签边框色**（用户明确要求）、连线本体（弱化色）、
    已连接的端口图元（着色 + 淡填充）；画布右上角提供对数刻度图例。
- **理由**：速率感知本身是对数关系（1G→2.5G 的差异感与 4G→10G 相当），
  线性映射会把 100M–1G 挤成一团、把 10G–100G 拉成一片绿。
- **代价**：红色同时被用于"链路不可用"的告警色，可能造成歧义 ——
  因此下行链路用亮度更低的红 + 标签写"不可用"，并且不画速率数字。
- **状态**：✅ 生效（2026-09-17）

## D-27 Ctrl/Shift 多选，并把"最后两台"填入诊断

- **背景**：用户要求"Ctrl+点击多选设备，选中多个时最后两台自动填入连通性诊断面板，
  先选中的为源设备"。
- **决策**：`selection.devices` 保持**点击顺序**（追加式，不排序不复用集合）；
  `applySelection` 是所有选择变更的唯一入口，在其中统一处理诊断联动：
  `devices.length >= 2` 时取 `[n-2]` 为源、`[n-1]` 为目标，并清空旧结果；
  不足两台时撤掉"来自选中设备"标记。`Ctrl`/`Cmd`/`Shift` 三种修饰键都走同一条追加逻辑。
- **理由**：把联动放在选择入口而不是每个动作里，避免"点选顺序丢失"这类只在某条路径上出现的 bug；
  `selection.devices` 用数组（而非 Set）正是为了保住"谁先选"这一语义。
- **代价**：框选/全选得到的顺序是设备 id 的字典序而非用户意图，此时"最后两台"没有语义 ——
  因此这类选择也会填诊断，只是那两台未必是用户心里想的两台（框选后手动 Ctrl 点两下即可）。
- **状态**：✅ 生效（2026-09-17）

## D-28 机柜 = 容器设备 + 挂载关系 + 按面显示的端口

- **背景**：用户要求新增机柜容器（可设 U 高）、机架式设备可放入并表现为正面视图、
  可翻转看背面、悬浮半透明、两面都可能有端口。
- **决策**：
  1. 机柜建模为 `kind: 'rack'` 的**设备**（有 `rack{heightU,flipped}`，无端口、不参与转发），
     于是容器与普通设备共用同一套选择/移动/删除/撤销/持久化机制，不需要第二套实体系统；
  2. 标题栏右侧的翻转控件是**图标按钮**（Lucide `rotate-3d`，26×20，表达"转动观察角度"），
     不写文字；与「正面/背面」文本之间按测量宽度**右对齐并留出固定间距**，
     名称可用宽度再由面标识反推 —— 三者不会互相压字。
     按钮尺寸与图标数据同源（`rackFlipButtonRect`），命中测试与绘制共用同一个矩形；
  3. 挂载关系写在设备侧：`mount{rackId,startU}`；挂载时把卡片坐标**同步**到对应 U 位，
     机柜移动时带着柜内设备一起移动（相对位置不变），拖出机柜自动下架；
  4. 端口带 `side: 'front'|'rear'`，上架设备**只显示与当前观察面一致的端口**；
     未上架设备两面都显示。端口的图元布局始终按"全部端口"计算，因此翻转时端口不跳动、
     连线锚点保持稳定；
  5. `RACK_UNIT_H = (NODE_H + 6) / 4 = 23`（**4U = 一张标准卡片**），机柜默认 24U（可调 8–48U）；
     机柜宽度**按真实 19″ 比例反推**（见 D-33）；**设备占几个 U 由设备自己决定**（见 D-31）。
- **理由**：让"容器"复用设备机制，是这一轮里节省最多工作量的决定；而"端口按面显示"用数据
  （`side`）驱动，避免了在渲染层写"正面画一半、背面画另一半"的分支。
- **代价**：
  - 24U 机柜在 100% 缩放下约 600 单位高，画布需要用适应视图/缩放配合；
  - 悬挂在"隐藏面"端口上的连线仍按该面自己的布局接入，视觉上会隐入机柜后面（可接受）；
  - 机柜顶部/底部的配电与理线区未建模。
- **状态**：✅ 生效（2026-09-17）

## D-29 命中与框选矩形必须按设备类型区分（机柜不是标准卡片）

- **背景**：这是本轮由端到端测试抓出的**真实缺陷**。命中测试原本一律用卡片的 152×86 矩形，
  而 12U 机柜是 236×1100+ 的高瘦容器 —— 于是机柜标题栏右侧的"翻转"按钮落在命中区之外，
  在画布上**点不到**（冒烟脚本报 `flippedByCanvasButton: false` 才暴露出来）。
- **决策**：新增 `hitRect(device)`：机柜返回 `rackRect`，其余返回卡片矩形；
  命中测试、框选判定、拖动吸附的参考框统一改用它。
- **理由**：几何命中必须与绘制使用同一套尺寸定义 —— 一旦"画的是一套、点的是另一套"，
  就只会表现为"某些地方点不动"这类极难定位的问题。
- **代价**：新增设备类型时要记得同步 `hitRect`（已在 `hitRect` 注释里写明）。
- **状态**：✅ 生效（2026-09-17）；回归覆盖：冒烟脚本 `flippedByCanvasButton`

## D-30 拖动阈值：单击不得移动卡片

- **背景**：用户反馈"单击选中设备时也会拖动卡片"。原因是 pointerdown 立即进入拖动状态，
  而坐标会被四舍五入到整数，1–2 像素的手抖就足以把卡片挪走一格。
- **决策**：拖动状态增加 `armed`；只有指针移动超过 **4 屏幕像素**才 `armed = true`，
  此刻才 `beginHistory` 并开始应用位移；未越阈值的抬起视为单击，提交一个空事务（不入历史）。
- **理由**：这是"能否放心点击"的体验底线；顺带让撤销历史不再被点击污染。
- **代价**：小于 4 像素的微调需要改用方向键或先放大画布（当前未提供方向键微调，已列入路线图）。
- **状态**：✅ 生效（2026-09-17）；回归覆盖：冒烟脚本 `clickDoesNotDrag.unmoved`

## D-31 设备高度按 U 数变化，而不是"一个设备 = 1U"

- **背景**：初版把 1U 与一张标准卡片绑定（`RACK_UNIT_H = NODE_H + 6`），
  用户指出"一个设备可以占据数 U 高度，具体高度在设备卡片中配置"。
- **决策**：
  1. `Device.rackUnits`（缺省 **4U = 一张标准卡片**，可调 4–24U）表达设备高度，
     目录里 `rackableU` 给出默认值（机架服务器/交换机 4U、框式 OLT 8U）；
     下限取 4U 是因为卡片要放下图标/名称/类型/地址与端口面板；
  2. **卡片高度由 U 数决定**：`cardHeightOf(device) = max(NODE_H, units × RACK_UNIT_H − 6)`，
     于是 `deviceRect` / 端口面板位置 / 命中矩形 / 框选 / 拖动吸附全部自动跟随，
     不需要为"多 U 卡片"再造一套布局；
  3. 多 U 卡片的中部补上"占几 U / 第几 U / 型号"信息（否则 4U 卡片会出现大片空白）；
  4. 上架按 **units** 找连续空位；已上架设备改高度时重新排位，装不下则自动下架并提示；
     机柜内跨占的 U 格画成一段高亮带，占用统计按 U 数累加。
- **理由**：把"高度"变成设备的一个普通属性，而不是渲染层的特例，
  是这套模型里最省事也最不容易出错的做法 —— 所有既有的几何代码都通过 `cardHeightOf` 自动适配。
- **代价**：
  - 卡片面板区在 24U 时会显得空旷（端口仍是一行/两行居中）；
  - 端口不随 U 分段分布（真实框式设备每个槽位一组端口），见 D-32 的取舍。
- **状态**：✅ 生效（2026-09-17，U 刻度已于同日按用户反馈调整为 4U = 一张卡片）；
  回归覆盖：`cardHeightForUnits` / `rackUnitsOf` / 连续空位 / 改高度重排 / 装不下下架

## D-32 端口画在面板上；设备级翻转只在"未上架且有背板端口"时出现

- **背景**：用户指出"设备的每个端口可以设置在前面板还是背板，你确实需要另外做一套端口布局，
  对于有背板端口的设备也显示翻转 IconButton"。
- **决策**：
  1. 端口**从卡片底边移到面板区**：`panelBand(device)` 给出「头部之下、底边之上」的区域
     （头部 54 单位，多 U 卡片再多 42 单位放"占几 U / 型号"），端口图元按行在面板区内**垂直居中**，
     端口名在图元下方；选档时同时校验**宽度**（行数不超上限）与**高度**（含标签放得下）；
  2. 电缆接入点仍在**卡片底边**（端口图元到卡片底边之间由"引出线"衔接），
     因此 `linkPath` / 流向动画 / 命中测试全都不用改 —— 这是把端口挪到面板却几乎零连带改动的关键；
  3. 设备自身的观察面用 `Device.flipped` 表达；**上架设备的观察面跟随机柜**
     （翻转机柜在物理上就是翻转柜内所有设备），所以上架设备不显示自己的翻转按钮；
  4. 翻转按钮与机柜同款（Lucide `rotate-3d`、26×20、右侧留间距、带「正面/背面」标识与悬浮提示），
     命中测试与绘制共用 `deviceFlipButtonRect`。
- **理由**："设备两面都有端口"这件事在数据层早就有了（`port.side`），缺的是**可见性与可切换入口**；
  用"面板区 + 设备翻转"把它补齐，比在两种端口布局之间做分支要简单得多。
- **代价**：
  - 多 U 设备的面板区会有留白（端口居中，不按 U 分段）；
  - 未上架设备的翻转是"视图状态"、不进撤销历史（与机柜翻转一致）。
- **状态**：✅ 生效（2026-09-17）；回归覆盖：面板区约束 / 4U 单行带标签 / 多 U 锚点 /
  上架设备跟随机柜 / 设备翻转（截图核对正背面端口）

## D-33 机柜宽度由真实 19″ 比例反推，上架卡片宽度跟随机柜

- **背景**：用户指出"当前宽度和每 U 的实际物理高度比例不对，放入机柜的设备卡片宽度也要遵循机柜宽度"。
  实际检查：原宽度 236 是按标准卡片宽度凑出来的，宽高比只有 236/23 ≈ 10.3 的"外框对 U 高"，
  而**设备面宽对 U 高**只有 152/23 ≈ 6.6 —— 真实 19″ 机架是 482.6/44.45 ≈ **10.86**，
  所以机柜看起来又瘦又高，上架卡片只占中间一条。
- **决策**：
  1. 由真实比例反推：`RACK_UNIT_H = 23` → `RACK_EQUIPMENT_W = round(23 × 10.86) = 250`
     → `RACK_W = round(250 × 1.24) = 310`，且**恰好**满足 `设备宽 + 2×(边框 + 导轨) = 外宽`
     （250 + 2×(12+18) = 310），导轨宽度不再是拍出来的；
  2. **卡片宽度也随挂载状态变化**：`cardWidthOf(device)` 上架时返回 250（铺满两导轨之间）、
     未上架返回 152，与 D-31 的 `cardHeightOf` 是同一套思路 —— 几何、命中、端口排布
     都通过这两个函数自动跟随；
  3. 端口行排布的可用宽度也随之变成 234，于是 27 口设备可以用**更大**的端口图元排两行
     （实测上架后行数不增加）。
- **理由**：比例是"像不像真的"的第一观感。用真实尺寸比值而不是手感数字，
  以后调整 U 高（比如为了更大的端口图元）时机柜宽度会自动跟着变，不需要重新凑数。
- **代价**：
  - 机柜更宽（310）也更占画布，24U 机柜约 310×600；
  - 上架卡片从 152 变 250，与未上架形态差异较大（这正是"机架设备"与"桌面设备"的形态差别，
    但同一台设备在上下架时尺寸会变化，需要在文档里说清楚）。
- **状态**：✅ 生效（2026-09-17）；回归覆盖：`RACK_EQUIPMENT_W / RACK_UNIT_H`、
  外宽分解式、`cardWidthOf`、4U 卡片宽高比、上架后端口行数不增加

## D-34 数字输入"输入期不钳制、提交时钳制"

- **背景**：用户实测报告两个问题：① 在机柜高度里输入 `42`，结果是 `48`；② 上下小三角最高只能到 24。
  根因是两条独立的缺陷：
  1. **每次按键就钳制**：输 `4` 立即被抬到下限 `8`，用户接着输 `2`，输入框里成了 `82`，
     再被抬到上限 `48` —— 多位数输入被彻底打断；
  2. **上下限写死在组件里**：机柜高度输入框的 `max` 还是旧的 `24`，
     与 store 里已经放宽到 8–48 的钳制不一致（`min`/`max` 不一致会让小三角停在错误的上界）。
- **决策**：
  1. `NumberInput` 改为**草稿语义**：`onChange` 只更新草稿文本，`onBlur` / `Enter` 才解析并提交，
     `Esc` 放弃；提交时的解析与钳制抽成纯函数 `commitNumberDraft`（可单测）；
  2. 外部值变化（撤销、切换选中对象）时丢弃草稿，避免显示过期文本；
  3. 鼠标滚轮在数字框上不改变数值（滚动页面时极易误改），改为失焦；
  4. **上下限只从常量取**：机柜高度用 `MIN/MAX_RACK_HEIGHT_U`（8–48）、设备 U 高用
     `MIN/MAX_RACK_UNITS`（4–24），并把范围写进字段提示，避免再次出现"提示、组件、store 三处不一致"。
- **理由**：受控数字输入框的"每次按键即提交"是一个典型的交互陷阱 —— 它对单击式输入没问题，
  对多位数输入必然出错。把"输入期"与"提交期"分开是唯一正确的做法，
  而且这个修复对所有数字字段（前缀、VLAN、线缆长度、信道）一次性生效。
- **代价**：
  - 输入期间输入框可能短暂显示超出范围的值（这是刻意的：不打断用户）；
  - 依赖失焦/回车提交，若用户输入后直接点画布（会失焦）也会提交 ✓，但若直接关窗口则丢弃（可接受）。
- **状态**：✅ 生效（2026-09-17）；回归覆盖：`commitNumberDraft` 单测 5 项 +
  冒烟脚本逐键输入 `42`/`99` 与两个字段的 `min`/`max` 属性

## D-35 文字绘制单列一层；节点树跟随画布；id 用"集合内唯一"而非时间戳

- **背景**：用户提出两件事，加上验证过程中被测试抓出的一个既有缺陷：
  ① 连线标签会被设备卡片盖住；② 需要一页能看全画布节点并排序的节点树；
  ③（测试副产物）`addDevice` 用 `Date.now()` 生成 id，同一毫秒内连续添加会撞 id。
- **决策**：
  1. **绘制分两趟**：线体、粒子、阻断脉冲在下层；**标签与文案统一在设备卡片与端口之后绘制**
     （`drawCable(..., 'stroke' | 'label')`、`drawFlow(..., 'under' | 'over')`）。
     不做"给每个标签加 z-index"式的补丁，而是让图层职责在函数签名上就分开；
  2. **节点树是画布的第二视图**，不是另一份数据：直接由 `buildNodeRows(world)` 派生，
     机柜作父节点、柜内设备按 U 位缩进；**排序只在同级内进行**，保证父子不被拆散；
     双击定位依赖 store 里的 `canvasSize`（画布用 ResizeObserver 上报），把设备算到视口正中；
  3. **id 生成改为"集合内唯一"**：以时间戳为基，若与现有集合冲突则追加序号，
     设备/线缆/端口三处统一走 `uniqueId()`。
- **理由**：
  - 图层靠"绘制顺序"而不是"每个元素自己争取"，才不会在新增元素时被再次破坏；
  - 节点树若另存一份数据就会与画布漂移，派生视图永远与画布一致；
  - 时间戳不是唯一性来源 —— 在脚本批量建图、快速拖入多台同型号设备时必然撞车，
    而这类 bug 的表现（React key 告警、Map 静默覆盖）非常隐蔽。
- **代价**：
  - 绘制多一趟遍历（线性开销，实测无感）；
  - 节点树对大拓扑（千级）需要虚拟滚动，当前是全量渲染；
  - `uniqueId` 依赖传入的"现有集合"，调用方必须传对（已在三处统一）。
- **状态**：✅ 生效（2026-09-17）；回归覆盖：像素采样的层级断言、节点树 8 项单测 + 冒烟 6 项、
  id 唯一性 2 项单测

## D-36 标签位置存"弧长比例"；绘制分趟但不引入图层系统

- **背景**：用户要求"允许手动拖拽调整连线标签在连线上的位置"。
  实现上有三个选择：存像素偏移、存"第几个采样点"、存**弧长比例**。
- **决策**：
  1. `Cable.labelRatio` 存**弧长比例**（0 = A 端端口，1 = B 端端口，缺省 0.5）；
  2. 拖拽时把光标**投影到折线上**（逐段求垂足，`nearestRatio`），而不是"找最近的采样点"；
  3. 比例钳制在 `[0.04, 0.96]`（两端留余量，避免标签被端口图元压住或跑出线外）；
  4. 靠近中点（屏幕 10px 内）**吸附回 0.5**，双击标签 = 复位；整段拖动算**一条历史**。
- **理由**：
  - **像素偏移**在缩放、拖动设备、改端口布局后就错位了 —— 标签会飘到线外；
  - **采样点下标**依赖曲线细分步数（`sampleCubic` 的 steps）：细分一改，标签就跳位置，
    而细分是绘制细节，不该成为数据契约（`sampleCubic` 目前 18 段，长为 100 的线
    两采样点间距可达十几像素，取最近点还会让拖动"一跳一跳"）；
  - **弧长比例**对细分、缩放、设备移动都稳定，且天然可序列化、可校验、可写测试；
  - 它是**纯展示属性**：不参与推演（`negotiateLink` 不看它），所以拖标签永远不会
    让诊断结论变化 —— 这一点有单测兜住。
- **代价**：
  - 标签位置依赖连线几何：两端设备被拖得很远时，标签按比例仍在中点，"相对位置"保持，
    但绝对位置当然会变（这正是想要的）；
  - 命中框是**固定屏幕尺寸**，因此世界尺寸要除以 `camera.k`：放大了更好点，
    这是刻意的（否则在小缩放下标签几乎点不中）。
- **状态**：✅ 生效（2026-09-17）；回归覆盖：折线弧长 7 项单测、标签几何/命中 5 项、store 3 项、
  端到端 8 项（含"拖标签不动设备"）

## D-37 标识只有一份几何来源；favicon 由脚本派生

- **背景**：用户要求"设计一个 Logo，同步到 favicon 和 README 顶部"。
  手工维护"一个大图 + 几个尺寸的 favicon"必然会漂移 —— 换了 mark 却忘了换 16px 那张。
- **决策**：
  1. `assets/brand/mark.svg` 是**唯一几何来源**；`apps/web/public/` 下的 favicon 与 PNG
     **全部由 `pnpm brand`（scripts/build-brand.mjs）生成**，文件头写明"勿手工编辑"；
  2. 字标拆成 `logo-on-dark.svg` / `logo-on-light.svg` 两份，README 用
     `<picture>` + `prefers-color-scheme` 选择 —— 不用 SVG 内部媒体查询：
     GitHub 的图片会经代理与缓存，内联媒体查询在部分客户端不生效；
  3. 字标里的图形标识用**嵌套 `<svg viewBox>`** 复用几何，而不是复制一份放大过的坐标；
     字标文字用系统字体栈渲染（不轮廓化），排版只依赖"基线 + 字号"，不写量出来的 x 坐标；
  4. PNG 由 Playwright 的 Chromium 渲染（"打开 → 元素截图"），不引入 sharp/resvg 这类原生依赖；

- **理由**：
  - 单一来源 + 派生脚本，才能让"改一次标识"是安全的；
  - 深/浅主题两份字标是唯一能在 GitHub 两种主题下都保证可读的做法；
  - 嵌套 viewBox 让"favicon 与字标里的 mark 一模一样"成为结构事实，而不是靠人工同步。
- **代价**：
  - `pnpm brand` 依赖 Playwright 的 Chromium（本仓其它验证脚本同一来源）；
  - 字标不是轮廓化的，换机器字宽会有细微差异（换来的是文案可编辑）。
- **状态**：✅ 生效（2026-09-17）；目视校验：`.verify/brand-preview.png`（16/24/32/48/96px +
  两种主题字标 + 标签栏模拟）

## D-38 "悬浮半透明"统一给机柜与设备；命中测试里容器让位于具体设备

- **背景**：用户提出"对于存在背面接口的设备，均可以鼠标悬浮进入半透明效果"。
  此前只有机柜悬浮会半透明（FR-36）。落地时发现两件事必须一起决定：
  ① 淡出的透明度值是不是另取一个？② 柜内设备"悬浮对象是谁"其实是不确定的。
- **决策**：
  1. 机柜与设备共用同一个 `HOVER_FADE = 0.42`，"悬浮 = 透视"是**一条**规则，
     不是两条相似规则；
  2. 参与条件就是数据：`hasRearPorts(device)`（有 `side === 'rear'` 的端口）。
     没有背板端口就不淡出 —— 淡出要有信息量，否则只是闪烁；
  3. 悬浮时**同时**画出另一面的幽灵端口（复用机柜已有的幽灵绘制路径）；
  4. `hitDevice` 改为**非机柜设备优先**：先找最具体的设备，都没中才落到机柜上；
  5. 指针离开画布清空所有悬浮态（新增 `onPointerLeave`），拖动进行中除外。
- **理由**：
  - **为什么必须先修命中测试**：机柜矩形罩住整个柜内设备，而 `world.ordered` 是
    id 字典序（与 z 序无关）。于是"悬浮柜内设备时淡出谁"完全取决于设备 id 的字典序 ——
    这种"行为"在改一次 id 生成规则后就会变，不可依赖。修成"具体设备优先"之后，
    顺序第一次成为**设计**而不是巧合（顺带修好了"柜内设备的端口不好点"这个更早的隐性问题）；
  - **为什么阈值取 0.42**：还能认出是哪台设备（轮廓、色条、位置都在），又足以看清它压住了什么；
  - **为什么上架设备也算**：它同样有背面（而且柜内设备往往只能看一面），
    悬浮淡出与"翻转整个机柜"是互补的两种查看方式；
  - **为什么离开画布要清**：状态挂在 React state 上，指针移出后没人再触发 `pointermove`，
    半透明会永久留着 —— 看起来像设备坏了。
- **代价**：
  - 悬浮柜内设备时，机柜（`rackUnder` 命中）也会一起淡出 —— 两处半透明叠加。
    这是既有规则的自然结果，视觉上偏"喧闹"，但信息正确；
  - 命中判定不再等价于"绘制顺序的逆序"，因此**绘制顺序与命中顺序被有意解耦**，
    以后新增覆盖型图元（弹层、提示框）时要按同样思路显式决定优先级。
- **状态**：✅ 生效（2026-09-17）；回归覆盖：命中测试 4 项单测、端到端像素断言 6 项
  （含"只有前面板端口不淡出"的负向对照与"指针离开画布"）

## D-39 连线摆动用"一个偏移弹簧"，画布动画按需唤醒

- **背景**：用户要求"引入平面物理效果，在拖拽设备时，设备间连线有物理摇晃效果"。
- **决策**：
  1. 每条连线只维护**一个二阶系统**（偏移 + 偏移速度），不是质点链、不做约束求解；
  2. 偏移加在两个**控制点**上：端点被端口钉死，中段位移 ≈ 0.75×偏移 —— 于是像"甩线"；
  3. 受力 = **端点位移冲量**（`v -= Δ·9`）+ 弹簧回零（stiffness 90）+ 阻尼（damping 7，欠阻尼）；
     输入速度上限 2600、线身速度上限 700、偏移上限 60 世界单位，并按线长缩幅（`span/160`，下限 0.25）；
  4. 物理只在 render 层：动画循环**按需唤醒**（"世界变了"就唤醒，静止即停），不做常驻 rAF；
  5. 从静止被唤醒的那一帧**折减**速度到 35%，而不是丢弃：一次很快的甩动可能整段都落在两帧之间，
     丢掉就等于"甩得越快越不动"（这是实测踩到的坑：慢拖 7.5、快甩 0.1）；
     折减同时避免"空闲两秒后瞬移"制造巨浪；
  6. 唤醒后至少再跑 3 帧 —— 否则"速度=0 且偏移=0"会让循环立刻停掉，物理永远不开始。
- **理由**：
  - 19 个采样点的质点链在帧率波动时会抖，还要为"线长守恒"调一堆参数；
    这里的状态可以直接单测（帧率无关、钳制、收敛），出问题一眼能看出是哪一项；
  - 也**试过**更直觉的"滞后"模型（偏移拉向与速度成正比的目标），但它对"单帧快甩"无响应，
    与"拖得越快甩得越远"的直觉相反，所以换成位移冲量；
  - 引擎的确定性约束（D-01）不受影响：物理只影响**画**，不参与任何推演，
    也不进入 `Scenario`（不是持久化字段）；
  - 常驻 rAF = 静止时白烧电；"世界变了"是唯一真实触发源（拖动、对齐、撤销、上架都算）。
- **代价**：极端瞬移（撤销、批量重排）会让连线甩一下 —— 用 `maxOffset` 兜住幅度，
  观感上反而像"设备被拽了一下"，可以接受。
- **状态**：✅ 生效（2026-09-17）；回归覆盖：物理 7 项单测 + 端到端 5 项（含换向与收敛）

## D-40 适应视图：留白用屏幕像素，"装得下"优先于"别缩太小"

- **背景**：用户反馈"「适应」视图算法有问题，应当尽量把可视区域完整装进视图区域内且不留过多空白"。
  旧实现用 `1200 / 内容宽`、`700 / 内容高` 算缩放 —— **真实的画布尺寸根本没参与**，
  于是宽屏留大片空白、窄窗装不下；留白还是加在**世界坐标**上的固定 80/60，
  小拓扑被这点留白顶成中间一小块；缩放下限写死 0.3，大拓扑必然溢出。
- **决策**：
  1. 内容范围 = **设备矩形 ∪ 连线折线**（电缆垂在卡片下方，只算卡片会把线尾切掉）；
  2. 缩放由**真实画布尺寸**算：`min(可用宽/内容宽, 可用高/内容高)`；
  3. 留白是**屏幕像素**（28px），并按比例**居中**；
  4. 上限 2（小内容不无限放大），下限只做数值兜底 0.02 —— 与交互滚轮的缩放下限**分开**。
- **理由**：留白的单位应该是"用户看到的空白"，而不是世界单位；"装得下"是这个功能的目的本身，
  与它冲突的上限一律让步（想看清细节的人自己会放大）。

## D-43 预置场景是登记过的产品内容；写场景时固定的三条建模语义

- **背景**：用户要求"增加多套预置场景，单击「预置场景」时弹出模态弹窗要求用户选择"。
  原来只有一套家庭场景，且按钮点下去**直接覆盖**当前拓扑。
- **决策**：
  1. `scenarios/index.ts` 是唯一登记处（key / name / summary / highlights / pitfall / build），
     场景按主题拆成独立文件；`resetScenario` 变成 `loadPreset(DEFAULT_PRESET_KEY)`
     的别名，启动兜底也走同一张表；
  2. **每个场景都是产品内容**：`presets.test.ts` 逐条验证"说明里承诺的行为"，

  3. 「预置场景」改为**先开弹窗再载入**：换场景会丢掉手上的图，必须先让用户看清要换什么；
     弹窗同时展示当前场景、规模与"有意留的坑"；
  4. 写场景时固定的三条引擎语义（记进 FR-55，并在场景注释里写明）：
     ① VLAN 要**两端都对上**（真实网络只给交换机口打标，M0 按两端同 VLAN 建模）；

  - 场景若没有测试，"说明说能演示 X，实际却不成立"是必然发生的（写这批场景时

  - 把"有意留的坑"写进场景并测"可修复"，等于把预置场景从"演示数据"升级成"排查教材"。
- **代价**：
  - 每加一套场景就要配一段测试与一段文案（这是刻意的成本）；
  - 场景文件较长（每套 150–250 行），因为它们必须是**自洽的地址规划**而不是随机连线。
- **状态**：✅ 生效（2026-09-17）；回归覆盖：场景 18 项单测 + store 3 项 + 端到端弹窗流程

## D-44 规模压测：位置专用快路径、拖动期间推迟落盘、细节分级、绘制与命中同判据

- **背景**：按要求新增"中型 IDC"预置场景（3 机房 × 24 柜 × 满配 ≈ **810 台设备 / 809 条链路**）。
  第一版做完，场景**能载入、能推演（16 ms）**，但一拖动就掉到 **3–10 FPS**
  （中位帧时间 100 ms、p90 250 ms）。于是先量后改。
- **决策（四项，全部由实测定位，不是猜的）**：
  1. **位置专用快路径** `mutatePositions`：设备坐标**不影响任何派生数据**
     （链路、地址、路由、广播域只看端口与配置），所以拖动只需换掉设备对象、
     **不必 `buildWorld`**。实测 `moveDevices` 一帧 **80.6 ms → 1.1 ms**。
     配套：设备对象必须**逐个浅克隆**（写时复制）——只复制数组会让 `fn` 改到
     历史快照里的同一批对象，撤销等于没撤（这个 bug 是单测抓出来的）；
  2. **拖动期间推迟落盘**：历史事务进行中不写 localStorage，提交时写一次。
     810 台设备的存档是 1 MB，每帧 `setItem` 是 6 ms + GC 压力；
  3. **细节分级（LOD）**：`k < 0.18` 只画结构，`k < 0.45` 才画端口与机柜 U 位格，
     `k < 0.4` 不画连线速率标签（选中/诊断路径除外）。同时给设备卡片、机柜、
     端口条带加**视口裁剪**，把机柜 U 位占用表从"每个机柜扫一遍全部设备"
     改成每帧一次共享；
  4. **绘制与命中必须同判据**：低缩放下标签已经不画，但它的命中矩形是
     "屏幕尺寸 ÷ 缩放"，在世界坐标里覆盖一大片 —— 于是"点设备"变成了"拖标签"，
     而拖标签走的是 `patchCable`（完整重建）。抽出 `cableLabelVisible` 给两边共用后，
     帧时间回到 16.7 ms。这一条与 FR-49 的"拖宽度边缘"是同一个原则：
     **看到什么就操作什么**。
- **理由**：
  - 规模问题必须**先量后改**：我最初猜是画布绘制，CPU profiler 的调用链直接指出
    真正的原因是"误命中标签 → `patchCable` → 每帧全量重建世界"；
  - "派生数据与坐标无关"是引擎的既有性质（buildWorld 不读 x/y），把它显式用起来，
    比"优化 buildWorld"划算得多；
  - LOD 不是偷工减料：低缩放下那些细节本来就不可辨认，画它们是纯浪费。
- **代价与仍然存在的限制**：
  - 拖动仍是**中位 33 ms / p90 83 ms**（约 30 FPS），剩余成本是"React 每帧重渲染整个界面
    + 画布全量重绘 809 条连线"。要再上一层楼需要：拖动时合并 React 更新、
    只重绘脏区域、把 `world` 的派生数据做成增量更新 —— 属于**后续性能专项**；
  - 节点树在 810 行时切换要 **576 ms**（全量 DOM，无虚拟滚动）—— 已记入已知缺口；
  - 快路径的契约是"`fn` 只改设备顶层字段"：改 `ports`/`l3` 等嵌套结构必须走 `mutate`。
- **状态**：✅ 生效（2026-09-17）；回归覆盖：IDC 场景 6 项单测（含结构与分层连通）、
  快路径 3 项单测（等价性、引用一致性、事务/撤销）、标签可见性 2 项单测、
  端到端性能预算（中位 < 40 ms、载入 < 400 ms）

## D-45 缩放上下限与适应视图分开；说明文字收进弹窗；分栏比例用像素下限夹住

- **背景**：用户提出三件事：① 最远只能缩到 25%，很多图看不到全景；
  ② 右下角那条常驻按键提示挤且占地方，应改为「?」按钮 + 教学弹窗（按键要用键帽图标）；
  ③ 右侧「检查器 / 连通性诊断」的高度比例要能拖。
- **决策**：
  1. **缩放上下限分两套**：交互缩放 `[MIN_ZOOM 0.05, MAX_ZOOM 4]`，
     适应视图 `[FIT_MIN_ZOOM 0.02, FIT_MAX_ZOOM 2]`。两者目的不同 ——
     适应视图的"装得下"可以让步到极小，交互缩放的下限是手感问题；
     25% 那道墙的根因就是两者共用了一个魔数；
  2. **画布上的常驻说明全部移除**，收进「?」弹窗：常驻文字在 380px 的侧栏 + 画布布局里
     永远会和内容抢地方，而它 90% 的时间没被读过；
  3. **键帽（keycap）而不是文字描述按键**：`Ctrl` `⇧` `Z` 三个键帽一眼可见"三键同按"，
     而 "Ctrl+Shift+Z" 要用户在脑子里拆；
  4. **分栏比例用像素下限夹住**（`clampPaneRatio`，纯函数 + 单测），
     并把这个偏好写进 localStorage；分割条做成 `role="separator"` + 方向键可调。
- **理由**：
  - "能不能缩到全景"是**能力问题**，不该被手感参数挡住；反过来，把两套界限合并也会
    让"装得下"永远做不到（这正是第十一轮修适应视图时踩过的同一个坑）；
  - 按键教学属于**低频高价值**信息：低频 → 不该常驻，高价值 → 要有清晰入口（「?」是共识）；
  - 下限用像素而不是比例：不同屏幕高度下，"20% 高度"可能是 100px 也可能是 400px，
    而"至少能显示两行端口信息"是一个像素事实。
- **代价**：
  - 缩放范围变大后，5% 时几乎看不到任何文字（只剩结构）—— 这是**刻意的**：
    要看细节请放大，LOD 保证低缩放下的绘制成本与观感（FR-57）；
  - 「?」弹窗需要维护一份与代码同步的操作清单：新增交互时要记得加一条
    （已在弹窗注释里写明这份清单的职责）。
- **状态**：✅ 生效（2026-09-17）；回归覆盖：分栏 5 项单测 + 端到端 14 项
  （缩放上下限、5% 下 IDC 全景、旧提示文案消失、弹窗键帽数量、拖动与夹取、落盘与刷新保持）

## D-47 部署基路径交给 CI 计算；仓库里不留任何绝对资源路径

- **背景**：用户要求"配置 GitHub CI（英文流程）、部署到 GitHub Pages，注意 baseURL"。
  GitHub Pages 的**项目站点**是子路径（`https://<owner>.github.io/<repo>/`），
  这是最容易翻车的一类部署：JS/CSS 404 直接白屏，favicon 与 manifest 静默 404。
- **决策**：
  1. `base` 由环境变量 `BASE_PATH` 注入，本地/普通构建默认 `/`；
     CI 里取 `actions/configure-pages` 的 `base_path` 输出（用户站点自动是 `/`，
     项目站点是 `/TopoSmith`），于是**换仓库名或换成用户站点都不需要改代码**；
  2. 引用资源一律走基路径感知的写法：`index.html` 用 Vite 的 `%BASE_URL%`，
     组件用 `import.meta.env.BASE_URL` —— `index.html` 的 5 个 favicon/manifest 链接
     与页眉里那枚 `<img src="/favicon.svg">` 全部改掉（后者是子路径下必然 404 的硬编码）；
  3. 单个 workflow 两个 job：`verify`（类型检查 + 两套单测 + 生产构建）与
     `deploy`（`needs: verify`、仅 main、`if` 排除 PR），权限最小化，
     `deploy` 才申请 `pages: write` / `id-token: write`；
  4. **验证方式不是"看 CI 绿了"**：本地用请求拦截把 `dist` 当成挂在
     `https://pages.test/TopoSmith/` 下的站点喂给浏览器，断言资源带前缀、
     页眉标识加载成功、无 404 与控制台错误。
- **理由**：
  - 基路径是**部署环境的事实**，不该硬编码进源码；交给 CI 计算才能同时支持项目站点与用户站点；
  - 绝对路径在本地开发下"看起来没问题"（base=`/` 时恰好正确），只有在子路径部署时才暴露 ——
    所以必须有**在子路径下真的打开一次**的验证，而不是只检查构建产物字符串；
  - `enablement: true` 让首次推送就能自行打开 Pages，不必先去 Settings 手点一遍。
- **代价**：
  - 多一个环境变量；本地若要复现线上路径需要显式 `BASE_PATH=/TopoSmith/ pnpm build`（README 已写）；
  - `vite.config.ts` 里读环境变量时没有 `@types/node`（本包 tsconfig 只有 DOM 类型），
    用一小段自带类型的读取函数代替引入 node 类型 —— 避免让应用代码也能"合法"使用 node 全局变量。
- **状态**：✅ 生效（2026-09-17）；验证：`.verify/pages-base.mjs`（子路径下启动 + 资源前缀断言）
