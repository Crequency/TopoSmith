# 地址、网段、VLAN、DHCP 与 DNS 模型

> 版本：v0.1（M0）

## 1. 地址从哪来

一台设备的有效地址（`Address`）有三个来源，优先级互斥、不叠加：

| 来源 | 适用 | 判定 |
|---|---|---|
| 静态接口 | 路由器/交换机/光猫/AP/服务器等基础设施 | `l3.interfaces[]` |
| 静态终端 | 终端设备手动配置 | `client.mode === 'static'` |
| DHCP 租约 | 终端设备自动获取 | `client.mode === 'dhcp'` → 推演结果 |

```
Address {
  ip, prefix, gateway?, dns[], portId,
  source: 'static' | 'dhcp',
  lease?: { serverId, pool, index } | { failure: ReasonCode, detail }
}
```

**为什么把 DHCP 结果并入地址模型**：上层（路由表、ARP、诊断）不应该关心地址来源。
合并之后"某设备有没有地址"是一个统一查询，`NO_SOURCE_ADDRESS` 与
`NO_DHCP_LEASE` 的区别只在失败时用于解释，不影响主流程。

## 2. 网段与掩码

- 掩码用前缀长度表示（0–32），引擎内部用 32 位无符号整数比较。
- **同网段判定**：`(ipA & mask) === (ipB & mask)`。
- **直连路由**由接口自动生成，用户不需要（也不能）手工添加。
- 跨网段通信**必须**有网关或明细路由，否则结论是 `NO_ROUTE`，而不是"莫名其妙不通"。

### 主机位为 0 / 广播地址
M0 不做地址合法性校验（允许用户填 `192.168.1.0/24` 给某台主机），
但会在设备检查器里给黄色提示。理由：教学场景下用户常故意这么填来验证工具行为，
硬性禁止反而挡住"我想看看会怎样"的探索。

## 3. VLAN 模型

| 端口角色 | 行为 | 配置字段 |
|---|---|---|
| `access` | 只承载一个 VLAN，收发不带标签 | `vlan`（PVID，默认 1） |
| `trunk` | 承载多个 VLAN，带标签 | `allowedVlans[]` |
| `lan` / `wan` / `uplink` | 等同于 access，语义化命名 | `vlan` |

广播域按 VLAN 划分（见 `05-engine.md` §2）。**跨 VLAN 必须经三层设备**：

```
PC-A (VLAN 10, 192.168.10.10/24)
PC-B (VLAN 20, 192.168.20.10/24)
       → 不同广播域、不同网段
       → 若无三层设备与网关：结论「两端不在同一广播域（VLAN 10 vs VLAN 20）」
```

VLAN 是 M0 里**最容易被忽视却最常导致"不通"**的字段，因此证据链必须显式打印
两端端口的 VLAN 承载情况，而不是只报一个"不通"。

## 4. DHCP 推演

DHCP 是**广播**协议，因此第一条硬约束是：**服务器必须与客户端在同一广播域**。
这不是简化，而是真实世界的核心约束，也是"为什么路由器另一头的 DHCP 分配不到地址"的标准答案。

```
dhcpLease(world, clientDevice):
  对客户端每个候选端口（有线优先，无线按关联）：
    domain = broadcastDomain(world, port, port.vlan ?? 1)
    candidates = domain 中 services.dhcp.enabled
                 且服务器自身接口地址与地址池同网段
                 且服务器接口端口在域内
    按 deviceId 字典序取第一个（确定性）
    无候选 → { failure: 'NO_DHCP_SERVER' }
    分配：poolStart + (客户端在域内的字典序序号)
    池耗尽 → { failure: 'POOL_EXHAUSTED' }
    返回 { ip, prefix, gateway: pool.gateway, dns: pool.dns, serverId, pool, index }
```

**地址分配的确定性**：不按"谁先请求"分配，而按**客户端 ID 字典序**确定偏移量。
这样同一拓扑每次打开得到相同地址，导入导出、回归测试、截图对比全都稳定。
代价是与真实 DHCP 的"先到先得"不同——这是一个有意识的取舍，写在
`DECISIONS.md` D-06。

## 5. DNS 模型

### 5.1 配置面

| 对象 | 字段 | 说明 |
|---|---|---|
| DNS 服务器 | `records[{name, ip}]` | 静态/权威记录，M0 为扁平命名空间（无 zone 嵌套） |
| DNS 服务器 | `forwarders[]` | 上游 DNS，按顺序尝试 |
| 客户端 | `client.dns[]` | 静态配置的 DNS；DHCP 客户端则由租约下发 |

### 5.2 解析顺序

```
1. 本机静态记录 → 命中即权威应答
2. 转发器（递归，visited 防环）
3. NXDOMAIN
```

### 5.3 缓存

- 缓存**存在会话里，不存在拓扑里**（见 `05-engine.md` §6）。
- TTL 固定 300 秒（M0）；同一次会话内第二次相同查询返回"缓存命中 + 剩余 TTL"。
- 用户可手动清空缓存以重现"冷启动解析路径"——这是教学上的关键开关。

### 5.4 与"可达性"的耦合

DNS 解析不是独立的字符串查表：**查询本身要走网络**。因此 `resolve` 内部调用
`trace` 验证到 DNS 服务器的可达性，并把结果作为证据链子链。

于是会出现这类真实且极有价值的结论：

> 域名解析失败 → 因为 DNS 服务器 `192.168.1.1` 不可达 → 因为客户端没有默认网关
> → 因为它在 VLAN 20 而网关在 VLAN 1。

一句话把三层问题串起来，这正是本产品要交付的东西。

## 6. 家庭场景的地址约定（预置场景 `scenarios/home.ts`）

| 设备 | 地址 | 说明 |
|---|---|---|
| 云出口 | `100.64.0.1/24` | 运营商侧，托管权威 DNS 与示例站点 |
| OLT | `100.64.0.2/24` | 提供 OLT 侧管理地址；PON 口面向光猫 |
| 光猫（路由模式） | WAN `100.64.0.10/24`（网关 `100.64.0.1`）；LAN `192.168.1.1/24` | NAT ✅；DHCP 池 `192.168.1.100–192.168.1.200`，下发网关 `192.168.1.1`、DNS `192.168.1.1` |
| 光猫 DNS | 转发器 → `100.64.0.1` | 演示"本地 DNS 转发 → 权威"的完整链路 |
| 交换机 / AP | 管理地址 `192.168.1.2` / `192.168.1.3` | 便于从任意终端 ping |
| 终端 | DHCP | 有线与无线各若干台 |

**为什么预置场景里要有"公网侧"**：没有公网目标，"NAT 转换点"与"DNS 转发链"
两个核心演示都跑不起来。这个场景不是装饰，它是产品的**自带冒烟测试**。
