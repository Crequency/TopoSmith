# 推演内核设计（Engine）

> 版本：v0.1（M0） ｜ 推演内核 Anvil（包名 `@toposmith/anvil`，源码在 `packages/engine/src/`）
> 本文档说明算法与**为什么这样设计**，而不是逐行复述代码。

## 0. 一次推演的全过程

```
Scenario ──buildWorld──► World ──diagnose──► DiagResult{ok, summary, steps[], hops[], metrics}
              │
              ├─ 1. 派生链路：每个 Cable + 两端 Port → Link{up, speedMbps, duplex, issues}
              ├─ 2. 地址分配：静态 / DHCP 租约 → Address[]（每台设备）
              └─ 3. 索引：deviceById、linkByPort、端口→设备
```

**`buildWorld` 是唯一一次全局计算**，之后所有诊断都在 `World` 上做局部搜索。
这样"改一个 IP 后所有诊断失效"是自然的（`scenario` 变 → `world` 重算），
不需要手工失效缓存。

## 1. 链路协商（`model.ts`）

```
1. 介质配对检查：线缆 family 与两端端口 medium 是否相容
     双绞线(cat*)  ↔ rj45 ✓
     光纤(lc-*)    ↔ sfp ✓ 且 ↔ pon ✓（PON 用的就是光纤）
     DAC           ↔ sfp ✓
     无线(wireless) ↔ wifi ✓
     rj45 ↔ sfp / pon ↔ 双绞线 → error：介质与线缆类别不匹配
2. 长度检查：lengthM > 线缆 maxLengthM → error：线缆超长（链路 down，不是降速）
3. 线缆能力：按 speedTiers 取该长度下的最高速率
4. 协商速率 = min(端口A速率, 端口B速率, 线缆能力)
5. 双工 = 任一端 half → half
6. 生成 issues：
     降速（协商值 < 两端端口中较小者）→ warn + 指明瓶颈来源（线缆 / 端口 / 对端）
```

无线链路特殊（见 §5.5）：

```
协商速率 = min(两端无线制式标称速率)     ← WiFi 看标准+频段，蜂窝看世代
双工 = half（空口是共享半双工介质）
lengthM 无意义，不参与超长判定；共享介质折扣不在这里扣（见 §5）

无线关联还要过四道"关联成不成立"的检查（任何一条 error 都让链路 down）：
  介质配对        wireless ↔ wifi
  制式相容        WiFi 终端 ↔ 蜂窝基站 → error：RADIO_TECH_MISMATCH
  网络标识        WiFi 比 SSID；蜂窝比 PLMN（两端都填且不一致 → error）
  覆盖判定        客户端必须在提供方的覆盖区域内（§5.5）→ 否则 error

## 2. 广播域（`l2/domain.ts`）

```
broadcastDomain(world, seedPort, vlan):
  从 seedPort 出发 BFS：
    跨过线缆到达对端端口 → 对端端口属于本域
      若对端设备是二层设备（switch / ap）→ 把该设备上**其他承载同一 VLAN 的端口**
      也并入本域并继续 BFS
      否则（router / ont / olt / cloud / 终端）→ 停止，该设备终结广播域
  返回域内全部 (device, port)
```

三个关键点：

1. **广播域的边界是三层设备**，不是"线的尽头"。这条规则决定了"跨网段必须配网关"是必然结论。
2. **VLAN 是域的划分依据**：access 口按 PVID，trunk 口按允许列表。两端 VLAN 不一致 →
   它们根本不在同一个域里，ARP 永远得不到响应。这是家庭/办公排障最高频的真实原因。
3. **家用网关内部是一台交换机**：路由模式的光猫/路由器，其 `role === 'lan'` 的端口（含 WLAN）
   在设备内部桥接成 VLAN 1 的广播域，三层接口浮在这个桥上（`bridgesLanPorts`，D-17）；
   桥接模式的光猫/路由器则整机视为透明网桥（`isL2Forwarder`）。缺了这条规则，
   "光猫的 WiFi 客户端拿不到光猫自己的 DHCP 地址"这种错误结论就会出现在产品里。
   **桥内的转发同样受 VLAN 约束**：一个被划到 VLAN 20 的 LAN 口不在这座 VLAN 1 的桥里 ——
   否则"路由器上分属两个 VLAN 的两个口"会被当成同一座桥，凭空造出环路（D-51）。
4. **无线在二层是"桥接"**：无线关联被建模为一根 `wireless` 类型的线缆，
   AP 把 WLAN 与 LAN 口桥接在同一个 VLAN 里。于是无线客户端不需要任何特殊处理就能参与
   BFS、ARP 与路径推演——**用同一条代码路径处理有线和无线**，这是这套模型最省事的地方。

### 二层环路（`l2/loop.ts`）—— "不做 STP"不等于"不告诉你成了环"

M0 不做 STP（D-14），但环路恰恰是用户最需要被指出来的拓扑错误：以太网帧没有 TTL，
一个二层环路会让广播帧永远转下去（广播风暴）。所以引擎把「这里成了环」这个**结论**算准，
把"风暴会怎样"讲清楚，而不是静默地按最短路近似（D-51）。判定规则五条：

1. **只在同一条 VLAN 内成环**：环上每个端口都要承载该 VLAN。VLAN 隔开的两个网段即使
   物理上绕成圈也不成环 —— 这是"风暴不跨 VLAN"的算法依据（预置场景用它作对照组，FR-68）。
2. **只有转发设备参与**：端主机（网卡）不转发帧，所以"主机接两根线到两台交换机"不成环；
   至于哪些端口在设备内部互通，**复用 `l2/domain.ts` 的同一套规则**（`forwardPortsWithin`），
   不允许两处各有一套真相。
3. **聚合链路收缩成一条逻辑链路**：同一对设备之间勾了 `bonded` 的并联线缆视为一条（LACP），
   于是"双上行做了聚合"不报环、"插了两根线却没做聚合"报环（FR-66 / D-50）。
4. **只算 up 的链路**：介质不匹配、超长的线缆本来就不通帧。
5. **不给风暴动力学**：帧速率、队列、收敛过程都不建模，只在结论里披露（见 07 §6）。

算法：按 VLAN 建"端口组图"（节点 = 设备内端口组，边 = 线缆 + 设备内部转发），
用 Tarjan 找**非桥边**（不在任何环上的边是桥，非桥边必然在环上），
再对每条非桥边做一次"去掉它之后的最短路"，得到一条**首尾闭合的代表环路径**，
供诊断与检查器直接展示（如 `一楼接入交换机 GE23 → 二楼接入交换机 GE23 → 二楼接入交换机 GE24 → 一楼接入交换机 GE24 → 一楼接入交换机 GE23`）。

两处工程细节：设备内部转发用**星形中心**表示（k 个端口连到 1 个虚拟节点，而不是 k(k-1)/2 全连接），
在"哪条线缆卷进了环"上完全等价但边数少一个数量级；只为"转发设备的端口 + 接了线的端口"建节点
（端主机上没插线的网卡永远进不了环）。非桥边集合是**完整**的（每条卷进环路的线缆都会挂告警），
代表性环的上限是 `MAX_REPORTED_LOOPS = 32`，避免病态拓扑拖慢建世界。
810 台设备的 IDC 场景实测：环路扫描约 **8 ms**（建世界 ~75 ms 中的一部分，见 FR-56 表）。

**ARP 解析**：在域内查找"持有目标 IP 的设备"，判定依据是该设备的
`Address[]`（静态接口或 DHCP 租约）中，`ip` 命中且其端口在本域内。

**但只解析出"是谁"还不够**：hop 记录的是三层转发决策，而交换机不做三层决策，
于是"笔记本 → 光猫"这一跳中间其实还穿过了 AP 与交换机两侧的链路。
因此 `traceDomainPath` 在 BFS 的同时**记录走过的链路序列**（`transitLinkIds`），
带宽瓶颈判定与流向动画都以它为准 —— 少了它，无线段 1201 Mbps 会掩盖真实的
千兆网线瓶颈，动画也会画成一条"飞过交换机"的直线（见 DECISIONS D-23）。
BFS 保证最短跳数，链路迭代按 id 字典序保证结果确定（D-07）。

## 3. 路由（`l3/routing.ts`）

路由表由三类条目合成（顺序即优先级，同前缀长度时 connected 胜出）：

| 来源 | dst | nextHop | 说明 |
|---|---|---|---|
| 直连 | 接口所在网段 | 无（直连） | 从 `Address` + 掩码推导 |
| 静态 | 用户配置 | 用户配置 | `l3.staticRoutes[]` |
| 默认 | `0.0.0.0/0` | 网关 | `l3.defaultGateway` 或终端的 `client.gateway` |

查找规则是标准的**最长前缀匹配**：33 位掩码表（0–32），从最长前缀开始逐级回退。
证据链里会打印"匹配到 192.168.2.0/24（前缀 24），而非默认路由（前缀 0）"，
让"为什么走了这条"变成可读的结论而不是黑箱。

## 4. 逐跳推演（`diag/trace.ts`）——ping 与 traceroute 是同一个算法

```
trace(world, srcDeviceId, dstIp):
  1. 取源地址；若源是 DHCP 客户端且租约失败 → 立即返回失败（原因码来自租约）
  2. cur = 源设备；ttl = 16
  3. 循环：
     a. dstIp 是本机地址？ → 到达，成功
     b. 查路由表（最长前缀）
          无匹配 → NO_ROUTE（附路由表摘要）
     c. 出接口是否有链路？ 无 → PORT_NOT_CONNECTED
          链路 down → LINK_DOWN（附 issues 文本：超长 / 介质不匹配）
     d. nextHopIp = 路由下一跳（直连则为目的 IP）
     e. 在出接口的 VLAN 域内 ARP 解析 nextHopIp
          找不到 → ARP_FAILED（附：域内有几台设备、分别是谁 —— 帮助用户发现"网线插错端口"）
     f. NAT 判定：cur 开启了 NAT 且出接口通往公网且源地址是私网 → 记录 SNAT 转换点
          源是私网、出接口是公网、但 cur 未开 NAT → NAT_MISSING（失败）
     g. 记录一跳（入/出接口、链路速率与介质、下一跳），cur = 命中的设备
  4. ttl 耗尽 → ROUTING_LOOP
```

**为什么 ping 与 traceroute 合并**：它们的信息需求是同一个（逐跳转发决策），
差别只在输出呈现。合并后"可达性"结论天然带着完整路径，
用户问"不通"时不需要再单独跑一次路径——这是本产品相对传统工具的体验优势。

**回程不做对称推演**。M0 采用"有 NAT 即视为有状态回程"的简化模型，
理由：真实回程依赖连接跟踪表，推演它需要引入连接状态，收益远小于成本。
该简化在结论区以脚注形式披露（见 `07-diagnostics.md` §6）。

## 5. 带宽与速率（`diag/bandwidth.ts`）

```
路径 = trace(...).hops
瓶颈 = min(各跳链路速率)              ← 这一跳就是用户真正要的答案
传播时延 = Σ(线缆长度 × 5 ns/m)        ← 铜/光同量级近似
处理时延 = Σ(每跳 0.05 ms)
无线附加 = Σ(每个无线跳 0.3 ms)         ← 空中接入开销
RTT      = 2 × 单向

有效吞吐 = 瓶颈 × 效率系数
  有线路径：0.95（以太网帧开销 + TCP/IP 开销）
  含无线跳：0.50，并再除以该无线段提供方上的并发终端数（共享半双工介质；
              WiFi 看"同一 AP 下的客户端"，蜂窝看"同一小区内的终端"—— 算法相同，
              文案分开：蜂窝的速率是**单用户峰值**，最容易被误读成"我能用这么多"）
```

无线链路的协商速率还可能被**覆盖判定**直接归零（关联不成立 → `speedMbps = 0`，见 §5.5）。

两个数字必须**分开呈现**：`协商速率`（链路能力）与`有效吞吐`（实际能用）。
把无线路径的协商 1201Mbps 直接当成"能用 1.2G"是最常见的误导，产品要主动纠正。

## 5.5 无线覆盖与关联判定（`model.ts` + `packages/schema`）

无线关联在这套模型里始终是**显式事实**（一根 `wireless` 线缆），覆盖范围回答的是另一个问题：
**这条关联成不成立**。二者分开，是这一节的全部要点。

```
覆盖几何（schema，纯函数，引擎与画布共用）：
  圆心 = 设备卡片中心（deviceCenter：卡片足迹的一部分，见 D-56）
  半径 = RadioCoverage.radiusM（米）× WORLD_UNITS_PER_METER(20) = 世界单位
  全向 omni  ：距离 ≤ 半径
  定向 sector：距离 ≤ 半径 且 |方位角 − azimuthDeg| ≤ angleDeg / 2
               方位角 0° = +X（画布右方），顺时针为正（与 atan2(dy,dx) 一致）

判定（negotiateLink 的 wireless 分支）：
  providers = 两端里"mode === 'ap' 且启用覆盖"的那些
  providers 为空            → 不做覆盖判定（旧场景/自定义设备的行为不变）
  否则：落在**任一** provider 的覆盖内即成立
        都不在 → error: WIRELESS_OUT_OF_COVERAGE（报文给出相距多少米、半径多少、还差几米）
```

四个刻意的设计选择：

1. **覆盖不自动建立关联**。圈进去了不等于连上了 —— 关联仍要用户显式拉一根无线链路出来。
   "画个圈就自动连上"会把这个工具从"推演你画的网络"变成"猜你想要的网络"。
2. **判定与绘制共用同一份几何**。圆心、半径、扇形的角度定义都来自 `packages/schema`，
   画布只是把同一组数字画出来。否则会出现"看着在圈里、判定说在圈外"这种最难查的不一致。
3. **精度只到"几何覆盖"**。没有墙、没有衰落、没有天线增益、没有干扰，
   也不建模 2.4G/5G 的穿透差异。这些是**已知简化**（NG-01 的同类），文档与界面都要写清楚：
   覆盖圈是"能服务到哪"的工程近似，不是场强仿真。
4. **半径是物理量（米），画布是示意图**。画布比例固定为 `1 米 = 20 世界单位`（D-56）：
   半径必须能换算成画布上的距离，否则"拖大覆盖范围"这个操作没有意义。
   有线线缆**不参与**这个换算（`Cable.lengthM` 是用户声明的物理事实，见 §3 的"降速与不通"）。

### 蜂窝（`lte` / `nr`）

基站与蜂窝终端复用同一套无线模型，只有三处不同：

| 维度 | WiFi | 蜂窝 |
|---|---|---|
| 标称速率 | 按 802.11 标准 + 频段（`wifiNominalMbps`） | 按世代：LTE 150 Mbps、NR 1000 Mbps |
| 网络标识 | SSID（大小写敏感） | PLMN（如 `46000`；两端都填且不一致 → `CELLULAR_PLMN_MISMATCH`） |
| 世代不同 | — | 按较低一代回落（`CELLULAR_RADIO_DOWNGRADE`，warn） |

- 速率取的是**单用户峰值**（LTE Cat.4 150M / NR 中频 1G），刻意不取载波聚合的实验室峰值 ——
  否则"5G 一定比有线快"会变成产品给出的错误结论；
- 5G 终端接入 4G 网络会回落到 LTE，4G 终端在 5G 网络下也只能用 LTE：
  两条都由 `min(两端标称)` 自然得出，不需要额外的世代规则；
- 基站是**二层设备**：把空口与回传口桥接在同一个 VLAN 里。真实蜂窝是隧道 + 独立的会话管理，
  这里刻意简化成"基站 = 一台无线口很宽的 AP"，好处是蜂窝终端能与回传段走完全相同的
  ARP/DHCP/路由代码路径（与 §2 的"无线只是一根线缆"一脉相承）。
  这个简化会在文档与设备说明里写出来，不让用户误以为我们在模拟 EPC/5GC。

## 6. DNS 解析（`dns.ts`）

```
resolve(world, srcDeviceId, name, cache?):
  1. 取源设备的 DNS 服务器列表（DHCP 租约下发的优先）
  2. 依次（M0 只取首个）查询：
     a. 该 IP 的设备是否存在、是否为 DNS 服务器 → 否则 NO_DNS_SERVICE
     b. 用 trace 验证"到该 DNS 的连通性"，把结果作为证据链的子链
     c. 命中静态记录 → 返回（标注"静态记录/权威应答"）
     d. 有 forwarders → 递归下一个 DNS（visited 集防环）
     e. 无记录且无转发器 → NXDOMAIN
  3. 缓存：命中则直接返回并标注 TTL；未命中走完整链路后写缓存
```

缓存**不进 `World`**：它不是拓扑事实，而是"这次会话里发生过什么"。
因此它由调用方（UI store）持有并作为参数传入——这样引擎保持纯函数，
同输入同输出（NFR-03），而缓存命中/过期这类会话行为仍可演示。
TTL 在 M0 固定 300 秒，M1 起可配。

## 7. 原因码（`diag/reasons.ts`）

原因码是**唯一文案来源**：引擎只产出码 + 结构化数据，UI 负责渲染。
好处是文案可一次性改成多语言（NFR-09），且测试可断言原因码而不依赖中文措辞。

完整清单与语义见 `07-diagnostics.md` §3。

## 8. 确定性与可测性

三条硬性纪律：

1. **不遍历 `Map`/`Set` 的插入序做决策**——凡涉及"选一个"的地方都按显式排序键
   （设备 ID 字典序）决定，避免依赖插入顺序造成结果漂移。
2. **不用 `Math.random`、不用 `Date.now`**——引擎内任何时间来源都必须由调用方传入。
3. **不 mutate 输入**——`buildWorld` 深拷贝必要字段，诊断不改 `World`。

由此，任意诊断结果可以逐字节回归：`docs` 里的场景 + 期望的 `steps[].code` 序列
就是测试断言（见 `packages/engine/src/__tests__`）。
